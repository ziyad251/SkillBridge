# LMS Project: Current Implementation and Interview Study Guide

This document describes the implementation currently present in the repository. It is based on the active source code, SQL schema, package files, routes, controllers, repositories, helpers, and frontend pages. It does not describe an ideal or redesigned architecture.

When a behavior cannot be established from the checked-in source, this document says: Not confirmed from the current implementation.

## 1. Project Overview

This is a learning management system (LMS) with two application roles represented in the code: regular users/students and instructors. Students can register, log in, browse courses, view course details, purchase paid courses through Razorpay, access courses, watch lectures, record progress, download a completion certificate, and create or manage reviews. Instructors can create and update courses, manage lecture curriculum, upload media, and view course-related student data returned by course queries.

The active backend persists application data in PostgreSQL using the node-postgres `pg` package and parameterized SQL. Neon is supported as the PostgreSQL provider through the `DATABASE_URL` connection string and SSL configuration. MongoDB/Mongoose remains in the dependency list and is used by migration and verification scripts, but the active API repository is PostgreSQL-based.

### High-level architecture

```text
React + React Router
        |
        v
Axios API client
        |
        v
Node.js + Express routes
        |
        v
Controllers
        |
        v
PostgreSQL repository using pg and parameterized SQL
        |
        v
PostgreSQL database, commonly hosted by Neon

External services:
- Cloudinary: uploaded course and lecture media
- Razorpay: paid-course order and payment processing
- JWT: stateless authentication tokens
- Puppeteer: server-side certificate PDF rendering
```

The server listens on `PORT`, defaulting to port 5000, and exposes `GET /health` for a basic service/database status response.

## 4. PostgreSQL Database

The schema creates ten important tables.

### `users`

Purpose: stores account identity and authentication data.

- Primary key: `id VARCHAR(64)`.
- Important columns: `user_name`, unique `user_email`, hashed `password`, `role` defaulting to `user`, and `created_at`.
- Constraints: `user_name`, `user_email`, `password`, and `role` are required; email is unique.
- Relationships: referenced by courses, enrollments, course_students, orders, course_progress, reviews, and certificates.
- Delete behavior: dependent records vary by relationship. Instructor ownership is restricted; many student records cascade.

### `courses`

Purpose: stores course metadata and instructor ownership.

- Primary key: `id VARCHAR(64)`.
- Important columns: `instructor_id`, title, category, level, primary language, subtitle, description, image, welcome message, pricing, objectives, `is_published`, timestamps.
- Foreign key: `instructor_id` references `users(id)` with `ON DELETE RESTRICT`.
- Indexes: `courses_instructor_idx` and `courses_category_idx`.
- Note: the repository maps the database `is_published` field to the misspelled API property `isPublised`.

### `lectures`

Purpose: stores ordered course curriculum items and Cloudinary media references.

- Primary key: `id VARCHAR(64)`.
- Foreign key: `course_id` references `courses(id)` with `ON DELETE CASCADE`.
- Important columns: `position`, title, `video_url`, `public_id`, `free_preview`, and `is_legacy`.
- Constraint: `(course_id, position)` is unique.
- Delete behavior: deleting a course deletes its lectures. Legacy lectures are excluded by active course queries and completion calculations.

### `enrollments`

Purpose: records a user's access/purchase relationship with a course.

- Primary key: auto-generated `id BIGSERIAL`.
- Foreign keys: `user_id` references users with `ON DELETE CASCADE`; `course_id` references courses with `ON DELETE CASCADE`.
- Important columns: course title/instructor snapshot, purchase date, image, and paid amount.
- Constraint: `(user_id, course_id)` is unique, preventing duplicate enrollment rows.

### `course_students`

Purpose: stores the instructor-facing student membership snapshot for a course.

- Composite primary key: `(course_id, student_id)`.
- Foreign keys: both course and student reference their parent tables with `ON DELETE CASCADE`.
- Important columns: student name/email, paid amount, and creation time.
- This is a junction table representing a many-to-many relationship between users and courses, with additional attributes.

### `orders`

Purpose: stores payment/order lifecycle information.

- Primary key: `id VARCHAR(64)`.
- Foreign keys: `user_id` references users with `ON DELETE RESTRICT`; nullable `course_id` references courses with `ON DELETE SET NULL`.
- Important columns: order/payment status, payment method, Razorpay payment ID, payer ID, course/user snapshots, course pricing, and dates.
- Indexes: `orders_user_idx` and `orders_payment_idx`.
- The schema does not define a check constraint for valid status strings.

### `course_progress`

Purpose: stores one overall progress record per user/course.

- Primary key: auto-generated `id BIGSERIAL`.
- Foreign keys: user and course, both `ON DELETE CASCADE`.
- Important columns: `completed`, `completion_date`.
- Constraint: `(user_id, course_id)` is unique.

### `lecture_progress`

Purpose: stores completion/viewing state for individual lectures.

- Composite primary key: `(progress_id, lecture_id)`.
- Foreign keys: `progress_id` references course_progress with `ON DELETE CASCADE`; `lecture_id` references lectures with `ON DELETE CASCADE`.
- Important columns: `viewed`, `date_viewed`.
- It is the child/detail table behind course-level progress.

### `reviews`

Purpose: stores user ratings and written reviews.

- Primary key: `id VARCHAR(64)`.
- Foreign keys: course and user, both `ON DELETE CASCADE`.
- Important columns: user name snapshot, integer rating, review text, timestamps.
- Constraints: rating must be between 1 and 5; `(course_id, user_id)` is unique.
- Index: `reviews_course_created_idx` on course and descending creation time.

### `certificates`

Purpose: stores generated certificate identity and completion information.

- Primary key: `id VARCHAR(64)`.
- Foreign keys: course and user, both `ON DELETE CASCADE`.
- Important columns: globally unique `certificate_id`, completion date, downloaded time, timestamps.
- Constraints: `certificate_id` is unique and `(course_id, user_id)` is unique.

### Relationship diagram

```text
users
  |-- courses (instructor_id)
  |-- enrollments -- courses
  |-- course_students -- courses
  |-- orders -- courses (nullable)
  |-- course_progress -- courses
  |                    |-- lecture_progress -- lectures -- courses
  |-- reviews -- courses
  |-- certificates -- courses
```

The schema uses foreign keys for referential integrity. It uses one-to-many relationships such as one instructor to many courses and one course to many lectures. It uses junction tables for user/course enrollment and instructor-side student membership. Unique constraints prevent duplicate user emails, duplicate enrollment, duplicate progress, duplicate reviews, duplicate certificates per course/user, and duplicate lecture positions within a course.

The schema is partly normalized: core relationships are separate tables, while order/enrollment/review rows intentionally keep snapshots such as course title, instructor name, and user name/email. This can preserve historical display data but can also become stale if source records change.

There are no explicit indexes shown for every foreign key. The exact query plan and runtime performance are Not confirmed from the current implementation.

## 5. Why PostgreSQL Instead of MongoDB?

This LMS has connected entities and rules: users own courses, courses contain ordered lectures, students enroll in courses, orders create enrollment, progress belongs to a user/course and individual lectures, and reviews/certificates belong to both users and courses. PostgreSQL expresses these relationships directly with foreign keys, joins, composite keys, unique constraints, and transactions.

MongoDB could model the same data, but the current design benefits from relational tables because:

- `JOIN` can combine course metadata with ordered lectures and course students.
- Foreign keys reject references to missing users, courses, lectures, or progress records.
- Unique constraints prevent duplicate enrollment, reviews, and certificates at the database boundary.
- Transactions group related changes, especially payment confirmation, course saving, and progress updates.
- Indexes support common lookups such as instructor courses, course categories, order payment IDs, and course review dates.
- Normalized tables avoid storing an entire lecture list inside every course document.

A concise interview answer: PostgreSQL fits because the LMS is relationship-heavy and requires consistency across payments, enrollment, progress, reviews, and certificates. The source uses direct `pg` queries rather than an ORM, so SQL, constraints, and transactions are visible in the repository.

## 6. Neon and Database Connection

Neon is a hosted PostgreSQL service. The application connects through the standard PostgreSQL `DATABASE_URL`; it does not use a Neon-specific client library. `server/config/postgres.js` creates a `pg.Pool` with that connection string. If a URL exists, SSL is configured with `rejectUnauthorized: false`.

The code checks the connection with `SELECT NOW()` during server startup and reports `connected` or `disconnected` in `/health`. Connection pool size and Neon deployment settings are Not confirmed from the current implementation. PostgreSQL is the database engine underneath Neon; Neon is the hosting/service layer.

Never place a real connection string or credentials in this document.

## 7. Backend Architecture and Request Flow

```text
Frontend request
   -> Express route
   -> optional JWT middleware
   -> controller
   -> PostgreSQL repository/helper
   -> database or external service
   -> JSON/PDF response
```

- Routes declare URL patterns and connect them to handlers.
- Middleware verifies a bearer JWT for the routes where it is attached.
- Controllers read request input, apply business checks, call repositories/services, and choose HTTP responses.
- The repository centralizes SQL, transactions, generated IDs, and conversion from snake_case database columns to API-shaped objects.
- Helpers integrate with Cloudinary and Puppeteer.

The repository uses `crypto.randomBytes(12).toString("hex")` for most string IDs. Course save, progress updates, progress reset, and payment confirmation explicitly use `BEGIN`, `COMMIT`, and `ROLLBACK`.

## 9. Authentication

```text
Register
  -> bcryptjs.hash(password, 10)
  -> INSERT users

Login
  -> SELECT user by email
  -> bcrypt.compare(password, stored hash)
  -> jwt.sign(user fields, JWT_SECRET, expiresIn 120m)

Frontend
  -> stores token in sessionStorage["accessToken"]
  -> Axios adds Authorization: Bearer token

Protected route
  -> middleware reads Authorization
  -> jwt.verify(token, JWT_SECRET)
  -> req.user = payload
  -> controller runs
```

The JWT payload contains `_id`, `userName`, `userEmail`, and `role`. The expiration is exactly 120 minutes. The code falls back to the literal `JWT_SECRET` if the environment variable is missing; this is a security weakness and should be fixed in production. The middleware verifies the token and returns status 401 for a missing or invalid token.

Role-aware redirects exist in the React `RouteGuard`, but server-side role authorization is not consistently implemented. In particular, instructor course and media routes do not attach the JWT middleware. Frontend route guards cannot protect direct API calls.

## 10. Paid Course Purchase Flow

The current flow is:

```text
Student chooses paid course
  -> frontend sends create-order data
  -> server inserts pending orders row
  -> server creates Razorpay order for amount * 100 INR
  -> Razorpay order ID is stored in orders.payment_id
  -> payment UI completes
  -> frontend sends Razorpay order ID, payment ID, signature
  -> server computes HMAC-SHA256(order_id|payment_id)
  -> signature comparison succeeds
  -> transaction marks order paid/confirmed
  -> transaction inserts enrollments row
  -> transaction inserts course_students row
  -> access lookup finds enrollment
```

Verification is necessary because the browser request alone is not proof that Razorpay accepted payment. The server checks the signature using the Razorpay secret. The database transaction prevents the order status from committing without the related enrollment/student records. Conflict handling makes repeated confirmation idempotent for enrollment and course-student rows.

Important limitation: order creation trusts client-supplied amount, user, and course data. The current code does not independently reload the course price or derive the user from a verified server-side identity for this endpoint. Also, the payment routes have no server auth middleware.

## 11. Free Courses

The progress controller treats a course with pricing equal to zero as accessible without an enrollment row. Paid courses require a matching enrollment for progress access. The frontend bypasses payment for free courses.

The repository does not create an `enrollments` row for the free-course path shown by the current implementation. Therefore a free course may be accessible in learning/progress behavior but may not appear in the enrollment-backed My Courses list. The exact review behavior for every free-course UI path is Not confirmed from the current implementation; the controller's paid-course enrollment check is the confirmed rule.

## 12. Progress Tracking

`course_progress` is the parent record for one user/course. `lecture_progress` stores viewed state for individual lectures.

When a lecture is marked viewed, the repository:

1. Begins a transaction.
2. Inserts or finds the unique user/course progress record.
3. Inserts or updates the lecture progress row with `viewed = TRUE` and the current timestamp.
4. Counts all non-legacy lectures for the course and all viewed lecture progress rows for that progress record.
5. Sets course completion to true only when total lectures is greater than zero and total equals viewed.
6. Sets `completion_date` once when complete, and clears it if the course is no longer complete.
7. Commits and returns the progress query.

Reset deletes child lecture progress and sets course completion false and completion date null in a transaction. The source does not show automatic certificate creation at the moment completion becomes true. Certificate availability is checked when the certificate endpoint is requested.

## 13. Reviews

Review creation requires a JWT. The controller verifies that the course exists, validates the rating, and requires enrollment for paid courses. The database also enforces rating 1 through 5 and a unique `(course_id, user_id)` pair, which prevents a second review for the same course/user.

Review updates and deletes include both the review ID and authenticated `req.user._id` in the SQL condition. This is the ownership check. Review retrieval is public and orders records by newest creation time; the course review controller also returns average rating and total count.

The exact validation rules for review text length are Not confirmed from the current implementation.

## 14. Certificate System

The certificate endpoint requires JWT authentication, enrollment, and completed course progress. The repository stores a certificate ID, course/user IDs, completion date, and download timestamp. Certificate IDs are generated using `LMS-` plus eight random bytes encoded as uppercase hexadecimal.

`createOrUpdateCertificate` inserts the certificate and sets `downloaded_at` to `NOW()`. If the same course/user already has a certificate, the conflict path updates the download timestamp. The certificate helper builds HTML and uses Puppeteer/Chromium to render a PDF. The controller returns the PDF as a downloadable attachment.

The exact PDF styling and runtime Chromium availability are Not confirmed beyond the checked-in `pdf-generator.js` implementation.

## 15. Cloudinary and Media Uploads

Cloudinary is used for uploaded course/lecture media. The helper reads `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET`. Course rows keep image URLs, while lecture rows keep `video_url` and `public_id` values.

Multer accepts a single `file` for `/media/upload` and up to ten `files` for `/media/bulk-upload`. The checked-in implementation writes uploaded files under `server/uploads` before Cloudinary processing. Temporary-file cleanup after upload is not present in the inspected helper/routes, so it should be reviewed for disk growth.

The source does not confirm an enforced file-size/type policy, server-side ownership check, or authenticated media endpoint.

## 16. Frontend Architecture

`client/src/main.jsx` mounts the React application and `BrowserRouter`. The active application state is owned in `App.jsx`, including authentication, student courses, bought courses, current progress, and instructor course-editor state.

Active client paths include:

- Public: `/`, `/auth`, `/courses`, `/course/details/:id`
- Student: `/home`, `/student-courses`, `/course-progress/:id`, `/profile`
- Instructor: `/instructor`, `/instructor/create-new-course`, `/instructor/edit-course/:courseId`
- Fallback: `*` to the not-found page

`RouteGuard` handles browser navigation based on authentication and role. It redirects unauthenticated users to `/auth`, regular users away from instructor pages, and instructors toward instructor pages except profile. It is a UI routing control, not API authorization.

`axiosInstance.js` uses `VITE_API_BASE_URL` or `http://127.0.0.1:5000`, enables `withCredentials`, reads `sessionStorage.accessToken`, and adds a bearer header. It removes the Content-Type header for FormData uploads. It logs request configuration and response/error details, which should be reduced in production because request configuration may contain sensitive information.

Auth, student, and instructor React context files exist, but `main.jsx` does not mount their providers. The active state path is `App.jsx`; the contexts should not be described as the active global state mechanism without further code changes.

## 18. SQL Concepts Visible in the Repository

- `SELECT`: finds users, courses, orders, reviews, certificates, enrollments, and progress.
- `INSERT`: creates users, courses, lectures, orders, enrollments, student memberships, progress, reviews, and certificates.
- `UPDATE`: changes courses, order payment status, review content, lecture viewed state, and completion state.
- `DELETE`: deletes old lectures during course save, review rows, lecture progress during reset, and Cloudinary media through the external API.
- `JOIN`: combines course progress with lecture progress and builds course-associated data through subqueries.
- `WHERE`: scopes queries by IDs, users, courses, payment IDs, and ownership.
- `ORDER BY`: sorts courses by configured price/title order, enrollments by purchase date, lectures by position, and reviews by creation time.
- Parameterized queries: `$1`, `$2`, and subsequent placeholders pass values separately from SQL text and reduce SQL injection risk.
- Transactions: `BEGIN`, `COMMIT`, and `ROLLBACK` protect multi-step course save, progress update/reset, and payment confirmation.
- `COUNT`: counts courses/orders and calculates total versus viewed lectures.
- Aggregation: `json_agg`, `json_build_object`, and review average/count create nested API data.
- `ON CONFLICT`: prevents duplicate user/course progress, enrollment, student membership, lecture progress, and certificates; course save uses upsert behavior.

One useful interview example is payment confirmation: an order update alone is insufficient, so the repository updates the order and inserts both access records in one transaction. If any statement fails, the catch block rolls back.

## 26. Deep-Dive Interview Answers

### Why PostgreSQL and not MongoDB?

Because the active schema has explicit relationships, composite uniqueness, foreign keys, ordered lectures, enrollment integrity, and multi-row transactions. PostgreSQL makes these rules enforceable in the database.

### Why not Prisma?

The current code uses `pg` directly and centralizes SQL in one repository. Prisma is not present in the package files, so claiming it would be inaccurate. Direct SQL gives the current code explicit control over joins, JSON aggregation, conflict clauses, and transactions.

### Why use `pg` directly?

It matches the current implementation and keeps SQL visible. It also allows direct use of PostgreSQL features such as `ANY`, `json_agg`, `ON CONFLICT`, and transactional clients.

### Where are transactions needed?

They are needed where several writes form one business operation: saving course plus lectures, marking progress plus completion, resetting progress, and payment confirmation plus enrollment/student membership.

### What if payment succeeds but enrollment insertion fails?

The PostgreSQL transaction rolls back the order/access writes, but the external payment is not automatically reversed. The system would need a retry/reconciliation or refund strategy. That recovery workflow is Not confirmed from the current implementation.

### How do foreign keys protect the database?

They reject references to missing parent rows and apply configured delete actions. For example, a lecture must reference an existing course, and deleting a course cascades to its dependent lecture rows.

### How does review restriction work?

The controller requires authentication, checks course/access rules, and the database unique constraint permits only one review per course/user. Update/delete additionally include the authenticated user ID in the SQL predicate.

### How is completion calculated?

The repository counts non-legacy lectures and counts viewed lecture-progress rows for the user's course progress. Completion is true only when there is at least one lecture and every lecture is viewed.

### What happens if a lecture is deleted?

The lecture's child progress rows cascade-delete because `lecture_progress.lecture_id` references `lectures(id) ON DELETE CASCADE`. Course progress itself remains unless its course/user is deleted.

### How would you prevent duplicate enrollment?

The schema already has `UNIQUE (user_id, course_id)`, and confirmation uses `ON CONFLICT DO NOTHING`. A stronger API would also authenticate the user and validate the trusted course ID server-side.

### How would you optimize a slow course query?

Inspect `EXPLAIN ANALYZE`, verify filters use indexes, consider indexes for frequent filters and joins, avoid returning unnecessary student/media data, and paginate course lists. Exact production query plans are Not confirmed.

### How would you test payment?

Unit test signature generation and mismatch handling; mock Razorpay order creation; run an integration test against a test database to verify order/enrollment atomicity; test retries and duplicate confirmation.

### How would you improve security?

Require JWT middleware on all sensitive routes, enforce role/ownership server-side, eliminate fallback secrets, validate request schemas, derive amounts/user identity from trusted records, constrain uploads, limit logs, and add rate limiting and secure deployment configuration. These improvements are recommendations, not current features.

## 27. Explain the Project in 60 Seconds

This is a React and Express learning management system backed by PostgreSQL. Students can register and log in with bcrypt-hashed passwords and a JWT, browse courses, access free courses, or purchase paid courses using Razorpay. After payment signature verification, the server transactionally confirms the order and creates enrollment records. Students can watch lectures, and the repository tracks lecture progress and marks the course complete when every non-legacy lecture is viewed. Completed students can download a Puppeteer-generated certificate and leave reviews subject to access and ownership rules. ## 28. Two-Minute Explanation

The frontend is a Vite React application using React Router. `App.jsx` owns the active authentication, student, and instructor state. Axios uses a configurable API base URL and automatically sends the JWT stored in sessionStorage. Route guards control browser navigation for students and instructors.

The backend is an Express API. Routes connect requests to controllers, and the controllers use a PostgreSQL repository. The schema has separate tables for users, courses, lectures, enrollments, orders, progress, reviews, and certificates. Foreign keys and unique constraints enforce important relationships. The repository uses parameterized SQL, joins and JSON aggregation for course data, and PostgreSQL transactions for course saving, progress changes, and payment confirmation.

For a paid course, the client asks the backend to create a pending order and Razorpay order. The client then submits Razorpay identifiers and a signature. The server verifies the HMAC signature, marks the order confirmed, and inserts enrollment and course-student records in one transaction. Progress is stored at course and lecture levels. When all non-legacy lectures are viewed, completion is stored and the certificate endpoint can generate a PDF. Cloudinary stores uploaded media, while Neon can host the PostgreSQL database.

The most important production gap is that UI route protection is not equivalent to backend authorization. The current server needs stronger authentication, role checks, ownership checks, trusted payment amount derivation, and validation.

## 29. Five-Minute Deep Explanation

I would start with the data model because it explains most of the application. `users` stores identity, password hash, and role. `courses` belongs to an instructor. `lectures` belongs to a course and has a unique position. `enrollments` represents a student/course access relationship and prevents duplicate pairs. `orders` keeps payment state and references the user and optionally the course. `course_progress` is unique per user/course, and `lecture_progress` records each viewed lecture. Reviews and certificates also use course/user relationships and have unique constraints to prevent duplicates.

The server uses `pg.Pool` and a repository instead of an ORM. This repository maps database snake_case to frontend-shaped objects and uses PostgreSQL features directly. Course queries use nested JSON aggregation for curriculum and students. The SQL is parameterized, and dynamic sorting is selected from a fixed allow-list. Transactions are used when several writes must succeed together.

Authentication hashes passwords with bcryptjs and signs a JWT containing the user identity and role for 120 minutes. Axios reads the token from sessionStorage and adds a bearer header. The JWT middleware verifies the token and places its payload on `req.user`. The frontend RouteGuard handles role-based redirects, but I would distinguish this from server authorization: several route files do not attach the middleware, so direct callers can bypass those UI checks.

The most important business transaction is payment. The client supplies order data, the backend creates a pending local order and a Razorpay order, and after payment the server verifies the signature. On success, one PostgreSQL transaction confirms the order and inserts enrollment and course-student records. This protects database consistency, although the current implementation still trusts too much client-supplied amount and identity data and has no confirmed recovery workflow for an external payment/database mismatch.

Progress uses a parent course record and child lecture records. Marking a lecture viewed runs in a transaction and calculates completion by comparing all non-legacy lectures with viewed lecture progress. Certificate generation is requested after enrollment and completion checks, then the server stores certificate metadata and renders a PDF with Puppeteer. Reviews require authentication and paid-course enrollment, and database ownership/uniqueness rules reinforce the controller checks.

For deployment, the client is built with Vite and the server is run by Node. Neon is simply the hosted PostgreSQL provider selected through `DATABASE_URL`; `pg` still speaks PostgreSQL. Cloudinary handles media, and Razorpay handles payments. Before calling the system production-ready, I would add server-side authorization everywhere, strict validation, secure mandatory secrets, better payment reconciliation, upload controls, and automated tests.
